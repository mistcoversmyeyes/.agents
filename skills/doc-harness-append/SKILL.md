# doc-harness-append

向已有的文档类 Harness 中新增信息，全程贯彻三个原则。

## 理论基础

操作前必须阅读 `references/doc-harness-theory.md`。理解以下核心概念：

- **三个原则**：信息增量、无法替代、地图线索
- **三个功能**：Cache（缓存可推导信息）、Constraint（约束 Agent 行为）、Context（提供必知上下文）
- **地图角色**：AGENTS.md 是唯一入口，companion 文件是深度内容，CLAUDE.md 是软链接
- **生命周期**：init → append → refactor → harden（本技能处于生命周期第二步）

后续步骤全部基于这些理论做决策。

## 前置检查 (Phase 0)

1. 检查 `.agents/AGENTS.md` 是否存在
2. 不存在 → 输出"当前项目没有 AGENTS.md，需要先用 `/doc-harness-init` 创建。"并中止
3. 存在 → 读取 AGENTS.md，解析文档地图，列出所有 companion 文件及其职责

## Phase 1: 理解新增内容

逐问引导用户，每次只问一个问题，等回答再继续：

1. **新增什么**：用一句话概括新增信息。示例："CI 流程新增了格式检查步骤"、"项目禁止在代码中硬编码 API Key"

2. **为什么 Agent 需要知道**：给出理由分类——
   - 信息增量：Agent 无法从代码/配置/README 自行推导的上下文。例："这个 SDK 的 v3 API 已被弃用，但 package.json 仍拉取 v3"
   - Cache：推导成本过高，需要缓存结论。例："整个 monorepo 只有 service-a 和 service-b 依赖 lib-x，其他包不依赖"
   - 约束：需要 Agent 在生成代码时遵守的规则。例："不允许往主分支直接推送"

3. **有多稳定**：最终结论还是暂定方案？
   - 稳定结论 → 直接写入
   - 暂定/实验性 → 标注 `暂定` 或 `TODO(harden)`，方便后续硬化

## Phase 2: 确定归属

用判断树逐层决策：

1. **信息增量检查**：Agent 能否从代码/package.json/README/目录结构中自行获取？
   - 能 → 不写入，指向已有文件说明"此处可查阅 XX 文件"
   - 不能 → 继续

2. **无法替代检查**：能否通过 git hook/lint/CI/类型系统/编译器检查机械执行？
   - 能 → 不写入文档，建议创建 harness 机制。引导使用 `/doc-harness-harden`
   - 不能 → 继续

3. **地图 vs 深度文档**：
   - 3-5 行内说清，且是任何操作的前置知识 → 放入 AGENTS.md
   - 超过 10 行，或属于独立专题 → companion 文件或新建独立文件
   - 内容属于已有 companion 文件范畴 → 追加到该文件末尾

4. **冲突检查**：
   - 与已有信息重叠？→ 合并写入，不建重复条目
   - 与已有信息矛盾？→ 标记两处冲突，请用户确认哪边正确

输出方案供用户确认：
```
## 写入方案
**内容类型**: <约束|决策记录|工作流说明|项目约定>
**推荐位置**: AGENTS.md 第 X 节|<companion-path>|新文件 <文件名>
**原因**: <用判断树简要推导>
**需修改现有内容**: <是/否>
```

## Phase 3: 冲突与重叠检查

写入前逐项核对：

- **重复检测**："这段信息在 AGENTS.md 第 X 行已存在……" → 只保留一份
- **矛盾检测**："现有文件说 A，您说 B，哪个正确？" → 请用户确认
- **冗余检测**："能写 5 个字而非 50 个字" → 压缩至最简
- **分散检测**：同一主题的信息是否散落多处？→ 合并至一处

## Phase 4: 写入

1. 按 Phase 2 确认的位置写入，始终最小编码：每句话自问"能更短吗？"
2. 标注稳定性：`TODO(harden)` / `稳定` / `暂定`
3. 新建文件务必保持格式与现有文件一致（frontmatter、标题层级、列表风格）
4. 写完后让用户预览变更

## Phase 5: 更新地图

若创建了新的 companion 文件：
1. 在 AGENTS.md 文档地图中增补引用行：`- [文件名](./文件名) — 一句话说明`
2. 确保 `.claude/CLAUDE.md` 作为软链接指向 AGENTS.md（不变）
3. 若无新文件，则跳过此阶段

## 反模式提醒

- 不新增能从代码/配置/Lint 规则推导的信息
- 不把已是 harness 约束的规则写成文档（应该直接硬化）
- 不把多个独立信息揉成一个段落 → 分点列表
- 不把简短信息写成复杂长句 → 一句话列完
- 不重复 AGENTS.md 中已有地图条目
- 不等用户问才解释术语 → 首次出现时附带简要定义

## 生命周期提示

- 追加的稳定约束后续可调用 `/doc-harness-harden` 硬化
- 追加导致结构分散可调用 `/doc-harness-refactor` 重整
- 误追加了可推导信息 → 调用本技能修正并标注删除

## Edge cases

- **新文件类型**：信息不属于任何已有 companion 范畴 → 询问用户是否创建新文件
- **格式不一致**：新增内容需修改现有文件的格式风格 → 询问是否统一重构
- **AGENTS.md 过长**：行数超过 150 → 建议先 `/doc-harness-refactor` 拆分再 append
- **用户犹豫**：用户不确定信息该放哪 → 用判断树逐层推导原因，只提供建议不做决定
- **批量追加**：用户一次性给出多项不同性质的信息 → 逐条走完 Phase 1-3 再批量写入
- **信息已存在**：用户想追加的内容已有但表述不准确 → 修改原条目而非新建
