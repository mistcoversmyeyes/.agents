# 文档类 Harness 理论基础

本文档定义文档类 Harness 的核心理论，供 `/doc-harness-*` 系列 skills 引用。

## Harness Engineering 框架背景

OpenAI 在 2026 年初提出 Harness Engineering 框架：

> **Agent = Model + Harness**

Harness 是围绕模型搭建的工程基础设施，含六大组件：文件系统、Bash 沙箱、**记忆**、Web Search + MCP、上下文工程、编排 + Hooks。

文档类 Harness 属于**记忆组件**。OpenAI 推荐的标准文件布局：

```
project-root/
├── AGENTS.md               # ~100行，导航入口（Agent 看到的第一个文件）
├── ARCHITECTURE.md          # 顶层架构图
├── SOUL.md / IDENTITY.md    # 身份与人格面具
├── PROGRESS.md              # 跨会话进度追踪
├── docs/
│   ├── golden-principles/   # DO/DON'T 模式文件
│   └── guides/              # 专项指南
├── .github/
│   ├── workflows/ci.yml     # CI 检查
│   ├── ISSUE_TEMPLATE/
│   └── PULL_REQUEST_TEMPLATE.md
└── .githooks/               # git hooks 自动化约束
```

## 文档类 Harness 的六类文件

| 文件 | 层次 | 作用 | 加载方式 |
|------|------|------|---------|
| `AGENTS.md` / `CLAUDE.md` | 指令与知识层 | 导航入口（~100 行），指向深层文档 | 每次会话自动注入 |
| `SOUL.md` / `IDENTITY.md` | 身份与灵魂层 | Agent 人格面具、语气风格、道德边界 | 通常自动注入 |
| `MEMORY.md` / `PROGRESS.md` | 状态与进度层 | 跨会话进度追踪、已完成/待办事项 | 按需读取 |
| `ARCHITECTURE.md` | 指令与知识层 | 顶层架构图、模块职责 | 按需读取 |
| `docs/` 下的原则/指南 | 指令与知识层 | DO/DON'T 模式、编码铁律、安全约束 | 按需读取 |
| `CONTRIBUTING.md` | 指令与知识层 | 贡献规范——如果可以 lint 化，就不该只写在这里 | 按需读取 |

始终加载的文件（AGENTS.md / SOUL.md）对信息密度的要求最高——每个 token 都在争夺宝贵的注意力预算。

## 三个原则

三个原则从 LLM 的本质（上下文窗口有限、具有推理和"解压缩"能力）推导而来。

### 信息增量原则

> 上下文窗口中已有的信息，除非需要强调，否则不要再引入。

LLM 的上下文窗口是稀缺资源。如果 Agent 已经从代码、package.json、项目结构中获取了某个信息，文档中就不该再重复——不管是 AGENTS.md 还是 ARCHITECTURE.md。每多一行冗余，就少一行真正有用的增量。

### 最小编码原则

> 在不完全丧失人类可读性的前提下，用说人话的最小编码传达完整信息。

大模型天然具备解压缩能力——给出关键信号，模型能还原完整语义。"最小编码"不是机器码，不是速记符号，不是为压缩而牺牲可读性。它是在"人一眼能看懂"和"不浪费一个 token"之间的最优平衡。

例：`blog` 分支仅写作提交 → 6 个字说清分支职责，不需要展开成段落。

### 无法替代原则

> 能被其他形式 harness 强制执行的信息，不应以文字形式留在文档类 Harness 中。文档里只保留无法替代的东西。

如果一个约束可以用 git hook 强制执行，就不该只写在文档里；如果一段命令速查等于 `pnpm run` 的输出，就该删掉让它去读 package.json。

约束有生命周期：模糊时先入文档，稳定后迁移到机械化执行。文档类 Harness 是约束的孵化器——不是终点，是中转站。

## 三个功能

原则回答"怎么判断"，功能回答"文档到底在做什么"。

| 功能 | 说明 | 与原则的关系 |
|------|------|------------|
| 1. 提供增量信息 | Agent 无法从代码自行推理：非标准约定、历史决策、Agent 行为约束 | 对应信息增量原则（同名但不同层） |
| 2. Cache 已有信息 | Agent 可推导但成本过高（多次 tool call、消耗上下文）的信息 | 与信息增量原则存在张力；是权衡后的例外 |
| 3. 提供约束 | 未成熟到可机械化的行为规则 | 关联无法替代原则——约束的入口，不是终点 |

原则和功能不是一一对应。最小编码原则渗透在所有功能的书写方式中。信息增量 vs Cache 的边界是一个开放的探索性问题——作者尚未完全厘清。

## AGENTS.md 的特殊角色：地图，而非百科全书

`AGENTS.md`（或 `CLAUDE.md`）是 Agent 看到的**第一个文件**。因此它不是百科全书，而是**地图**：用最小编码指明"什么东西在哪里"，让 Agent 按需渐进式加载深层文档。典型长度 ~100 行。

三个原则的**校准强度**因文件角色而异：
- AGENTS.md（地图）：最小编码原则拉到最紧——每个 token 都要争
- 深层文档（百科全书）：可在可读性和密度之间留更多呼吸空间
- 信息增量原则和无法替代原则：对所有文件一视同仁——冗余就是冗余

Cache 在地图中的位置：指针（"去看 package.json"）是地图的天然内容；高频 route 的直接标注（如"blog 分支仅写作提交"）是 cache——每行 cache 都在和信息增量争夺同一份 ~100 行预算。

## 生命周期状态机

文档类 Harness 的两种状态和四种操作：

```
                       ┌──────────────────────────────────┐
                       │         append (增量追加)          │
                       │   存在 ────────────────→ 存在     │
                       └──────────────────────────────────┘

   ┌──────────┐  init   ┌──────────┐  harden  ┌──────────────┐
   │ 不存在    │ ──────→ │   存在    │ ────────→ │ 存在 (更健康)  │
   └──────────┘         └──────────┘           └──────────────┘
                              │                        ↑
                              │       refactor         │
                              └────────────────────────┘
                               (拆分、合并、修剪、迁移)
```

四种操作：

| 操作 | Skill | 说明 |
|------|-------|------|
| **init** | `/doc-harness-init` | 从零创建文档类 Harness（不存在→存在） |
| **append** | `/doc-harness-append` | 向已有文档新增内容（存在→存在） |
| **refactor** | `/doc-harness-refactor` | 重构文档结构：拆分、合并、修剪、迁移 |
| **harden** | `/doc-harness-harden` | 将文档中的约束迁移到 git hook / lint / CI |

## 约束生命周期

约束的成熟度驱动其存在形式：

```
模糊约束 ──→ 稳定的文字约束 ──→ 机械化的 harness
  │              │                    │
  │   写在文档中   │   写在文档中        │   git hook / lint / CI
  │   TODO(harden) │   准备迁移         │   从文档中删除
```

- 模糊阶段：以文字形式写入 AGENTS.md，标注 `<!-- TODO(harden): 稳定后迁移 -->`
- 稳定阶段：文字描述已固化，可以通过 `/doc-harness-harden` 迁移到机械化形式
- 机械化后：从文档中删除或精简为一行引用（"格式由 `.githooks/commit-msg` 自动校验"）

## 不可替代的文档内容

以下内容无法被机械化替代，应当保留在文档中：
- 设计意图与历史决策（"为什么选了 A 而不是 B"）
- 项目特有的上下文（Agent 无法从代码推导）
- 作者视角与风格偏好
- 架构决策与权衡
- 领域知识（外部知识，Agent 训练数据中可能有但不可靠）
- 演进中的软约束（尚未稳定，不宜硬化）
