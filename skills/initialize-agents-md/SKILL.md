# Initialize AGENTS.md

从零创建 AGENTS.md，每一步都贯彻三个原则和三个功能。

## 核心哲学

三个原则（从 LLM 本质推导）：
- **信息增量原则**：上下文窗口中已有的信息不再重复。每行都应提供 Agent 无法从代码、package.json、项目结构中自行获取的信息。
- **最小编码原则**：在不丧失人类可读性的前提下，说人话的最小编码。大模型能解压缩——给关键信号，不给冗余描述。
- **无法替代原则**：能被机械化的约束不该以文字形式存在于 AGENTS.md。但约束有生命周期：模糊时先入此文件，稳定后迁移到 harness。

三个功能（AGENTS.md 的实际作用）：
- **提供增量信息**：Agent 无法自行推理的——项目特有的非标准约定、历史决策与设计意图、Agent 行为约束
- **Cache 已有信息**：Agent 可以推导但推导成本过高（多次 tool call、消耗上下文窗口）的信息。这是权衡后的例外，不是默认行为
- **提供约束**：尚未成熟到可机械化的行为规则。AGENTS.md 是约束的入口，不是终点

## 工作流

### Phase 1: 了解项目

逐个询问以下问题（每次一个问题，不要一次性抛出一堆）：

1. **项目是什么**：一句话描述这个项目做什么
2. **技术栈**：主要语言、框架、工具。只需名字，不需要版本号（package.json 里有）
3. **非标准约定**：这个项目有什么和同类项目不同的约定或做法？比如特殊的目录结构、非典型的模块组织方式
4. **关键决策**：有没有"为什么选了 A 而不是 B"的历史决策？这些决策的上下文不在代码里
5. **已有的项目文件**：有没有 README、CONTRIBUTING、package.json 等？引导 Agent 去读这些文件而非在 AGENTS.md 中重复

### Phase 2: 逐节构建

按以下顺序构建每个小节。每个小节写完后展示给用户确认。

#### 2.1 项目上下文（增量信息）

引导用户回答：Agent 无法从代码中推导什么？

- 项目的非标准约定
- 历史决策及原因
- 项目特有的"潜规则"

**每写一行，追问自己**：Agent 能从代码/package.json/README 中得到这个信息吗？如果能，删除此行或改为引用。

#### 2.2 技术栈与工具（最小编码 + Cache）

只包含：
- 主要语言和框架名（一行）
- 非标准的工具选择（如用了非主流的构建工具）
- 指向 package.json / Cargo.toml / 等配置文件的引用

**排除**：
- 版本号
- 能从 lockfile 推导的依赖列表
- 标准命令（它们应该在 package.json scripts 中自文档化）

#### 2.3 约束与约定（无法替代原则）

对用户提出的每个约束，做三问判断：

1. **这个约束稳定了吗？** → 如果还在演变，标注 "TODO: 稳定后考虑迁移到 harness"
2. **能被机械化吗？** → 如果是提交格式，建议创建 commit-msg hook 而非写入 AGENTS.md；如果是代码风格，建议配置 lint 规则
3. **如果都不能替代** → 以最小编码写入 AGENTS.md

对于"暂时模糊、以后会迁移"的约束，在 AGENTS.md 中用注释标注：
```markdown
<!-- TODO(harden): 约束稳定后迁移到 .githooks/pre-commit -->
```

#### 2.4 命令与工作流（最小编码）

不列出 `pnpm dev`、`pnpm build` 等标准命令——让 Agent 读 `package.json` 或运行 `pnpm run`。

仅包含：
- 非标准工作流（如"发布前需要运行 X 脚本生成 Y"）
- 需要多步骤配合的流程简要描述

### Phase 3: 原则审查

完成初稿后，逐节审阅：

1. **信息增量检查**：每行问"Agent 能从别处得到这个吗？"
2. **最小编码检查**：每行问"能用人话更简短地表达吗？"
3. **无法替代检查**：每段约束问"这能被 git hook / lint / CI 强制执行吗？"

审查中发现的问题，直接修改并告知用户。

### Phase 4: 写入文件

1. 将内容写入 `.agents/AGENTS.md`
2. 创建 `.claude/CLAUDE.md` 软链接指向 `.agents/AGENTS.md`
3. 如果约束小节中有 `TODO(harden)` 标注，提醒用户："以下约束目前以文字形式存在，稳定后可用 `/harden-agents-md` 审计并迁移到 harness"
4. 展示文件内容和统计（行数、对比典型 AGENTS.md 的密度）

## 风格指南

写出的 AGENTS.md 应体现：
- **密度高但不晦涩**：不给废话，但每句人一眼能看懂
- **引用而非重复**：能指向已有文件的内容，只写文件路径而非复制内容
- **标注迁移意图**：模糊约束标注 TODO(harden)，已稳定但未迁移的标注为何暂不迁移
- **中文为主**：用户说中文，Agent 能读中文，就写中文

## 反模式提醒

在构建每个小节时，主动阻止以下情况：
- 列出所有 npm scripts → 引导去读 package.json
- 大段编码规范 → 建议创建 lint 配置
- 详细的安装/构建步骤 → 这些应该在 README
- 技术栈版本号列表 → package.json 已包含
- /init 生成的样板内容 → 没有任何信息增量的空话

## Edge cases

- **已有 AGENTS.md**：询问是覆盖还是合并。如合并，先对已有文件做快速审计，只添加增量。
- **没有 package.json 的项目**：命令和工作流可以适当多写，因为没有可引用的 scripts 字段。
- **Monorepo**：询问用户是为根目录还是为子包创建，结构可能不同。
- **用户想跳过某节**：允许。不强制填满所有小节——空的 AGENTS.md 比满的废话 AGENTS.md 更好。
